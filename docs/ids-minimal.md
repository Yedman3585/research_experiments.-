# Минимальный IDS placement experiment

Это проверяемый стартовый эксперимент, а не воспроизведение Q-GARS и не новый
исследовательский метод. Источник архитектурного паттерна и квадратных штрафов:
[Zhang & Emu, Q-GARS, §4.1–4.2](https://arxiv.org/html/2603.23127v1#S4).

## Область модели

Один конечный батч из шести **уже готовых** окон признаков находится на edge.
Фиксированные реплики IDS расположены на edge, fog и cloud. Выбирается реплика
для каждого окна. Вычисление признаков и сбор alert пока за границами модели;
измеряем время от готовности окна до **завершения inference**, без обратной доставки
результата. Реальная нейросеть и реальные сетевые атаки пока не запускаются.
Входы — синтетические MI, байты, относительные дедлайны и заданные приоритеты.
Приоритет не является истинной меткой атаки.

Используются настоящие iFogSim `FogDevice`, `Application`, `AppModule`, `Tuple`,
сетевые uplink-очереди и CloudSim CPU time sharing. Топология — цепочка
edge → fog → cloud. Все задачи поступают одновременно, без фоновой нагрузки.
Из-за малого батча полный перебор допустим; задача ограничена 1–8 окнами в CLI.

Единицы согласованы: модельное время — секунды; работа — MI; скорость — MI/s
(MIPS); размеры — bytes; пропускная способность — bytes/s. iFogSim вычисляет
сетевую задержку как размер/скорость плюс propagation latency: дополнительного
перевода бит/байт нет. Комментарии upstream-примеров про миллисекунды не используются.
RAM реплик фиксирована (128 MB на реплику при 4096 MB на узел); RAM, энергия,
облачная стоимость и выбор модели IDS в оптимизацию пока не входят.

## Что заимствовано, а что адаптировано

В Q-GARS `x[v,r]` назначает задаче ранг; оба one-hot штрафа кодируют перестановку.
Здесь `y[i,m]` назначает задачу **узлу**. У каждого окна ровно один узел, но на
узле может быть несколько окон: переносить второй permutation-штраф было бы ошибкой.
Активное окно здесь — весь конечный батч, не обучаемый top-K selector.

Пусть `d_i` — целое число единиц работы по `u=1000 MI`, а `C_m` — целый
бюджет работы узла. Конфигурация проверяет `u C_m <= MIPS_m H`, где `H=2 s`.
Это **бюджет допуска работы**, а не мгновенная CPU/RAM capacity и не гарантия
завершить всё за H: сеть и совместное выполнение влияют на реальные задержки.

Ограничения:

\[
\sum_m y_{im}=1,\qquad \sum_i d_i y_{im}\le C_m.
\]

Прогноз без очередей:

\[
\hat\ell_{im}=\sum_{e\in path(edge,m)}(latency_e+bytes_i/bandwidth_e)
 +ud_i/MIPS_m.
\]

Положительная линейная стоимость и положительный парный proxy конкуренции:

\[
c_{im}=w_i[\hat\ell_{im}+\alpha\max(0,\hat\ell_{im}-D_i)],
\quad h_{ijm}=\beta(w_i+w_j)u\min(d_i,d_j)/MIPS_m.
\]

\[
f(y)=\sum_{im}c_{im}y_{im}+\sum_m\sum_{i<j}h_{ijm}y_{im}y_{jm}.
\]

Это **наша минимальная адаптация суррогатной цели**, не формула latency из Q-GARS
и не точное описание процессорного/сетевого расписания. Реальные очереди
оцениваются только в симуляции. Минимум f не обязан минимизировать фактическую latency.

Для каждого узла вводится целочисленный slack `s_m` в диапазоне `[0,C_m]`:

\[
E(y,s)=f(y)+P\sum_i(\sum_m y_{im}-1)^2
 +P\sum_m(\sum_i d_i y_{im}+s_m-C_m)^2.
\]

Slack кодируется ограниченным двоичным набором весов: например, для C=4 это
`[1,2,1]`; все числа 0…4 представимы, 5 не представимо. Квадрат раскрывается
с использованием `x²=x`. Файл QUBO хранит **верхний треугольник**:
`E=offset+sum(Q[i,j]*x[i]*x[j], i<=j)`; множитель 2 уже включён в cross terms.

## Штраф с проверяемым достаточным условием

Формулу динамического штрафа Q-GARS для permutation не переносим без доказательства.
Строим допустимое greedy-назначение и вычисляем его стоимость U; берём `P=U+1`.
Все коэффициенты f неотрицательны. Любое нарушение имеет ненулевой целочисленный
остаток, значит E≥P>U. Существует допустимая кодировка со значением U, поэтому
**глобальный** минимум QUBO допустим. Это не обещание, что SA найдёт этот минимум:
результат декодируется и проверяется, допустимый incumbent сохраняется.
Большие штрафы могут затруднять поиск; это консервативная стартовая формулировка.

Greedy назначает сначала наиболее тяжёлые задачи (при равенстве — более
приоритетные), выбирая допустимый узел по incremental surrogate cost. Для некоторых
допустимых packing-инстансов greedy может зайти в тупик: CLI явно завершится
ошибкой, а не выдаст недопустимое решение. Универсального admission/rejection пока нет.

## Решатель и проверка

Реализован seeded classical Metropolis **simulated annealing (SA)** на Python,
без внешних зависимостей. Это не SQA, не квантовое оборудование и не реализация
solver backend авторов. Один read начинает с greedy, остальные — со случайных
битов. Сохраняется лучший sample каждого read, затем проверяется назначение.
Точный oracle перебирает назначения `3^N`; он оценивает тот же surrogate с теми
же ограничениями, а не реальную симуляцию. Он не участвует в выборе результата SA.

Тесты проверяют раскрытие QUBO на всех битовых строках малого инстанса,
совпадение с исходной целью для всех допустимых назначений примера, slack,
воспроизводимость SA. Java integration tests проверяют одиночное выполнение,
время передачи в cloud, разделение CPU, delay планировщика, незавершённые задачи.

## CPU-адаптер для закреплённого iFogSim

Upstream `TupleScheduler` наследует пустой `getCurrentRequestedMips()`.
При обновлении `PowerHost` это обнуляло выделение CPU, и конечный батч не завершался.
Локальный `InferenceScheduler` переопределяет только запрос MIPS: полный CPU узла
при наличии задач, ноль в простое. Одна реплика на узел делит CPU между задачами
через стандартный `CloudletSchedulerTimeShared`. Изменений в vendor нет.
Это явная часть модели, подтверждённая аналитическими integration tests.

## Время решения и связь Java/Python

CSV здесь — файловый контракт батча, не постоянный RPC-мост. Python вычисляет
назначения до запуска JVM; Java воспроизводит их в модельном времени.

Четыре запуска на одинаковых входах:

- `greedy`, `qubo_sa`: delay=0, изоляция эффекта назначения; не end-to-end оценка.
- `greedy_with_delay`, `qubo_sa_with_delay`: вводят измеренную стоимость решения
  как ожидание от release до отправки окон в edge. Дедлайн считается от release.

Для SA учитываются построение incumbent, сборка QUBO, кодирование, SA и декодирование.
Oracle, запись артефактов, javac и старт JVM исключены из decision delay как расходы
текущего испытательного стенда. Время процесса Java показывается отдельно;
это **не измерение RPC latency**. Перенос measured delay в симуляцию — модель
выделенного CPU планировщика, не одновременный запуск Java и Python.
Без фоновой нагрузки этот батч пока не исследует устаревание состояния.

Дедлайны считаются с численной погрешностью 10 микросекунд; CPU update interval
равен 0.01 s. Незавершённые к фиксированному горизонту задачи всегда считаются
просроченными. Среднее/максимум latency считаются только по завершённым и помечены
соответственно. Время инференса берётся по `CLOUDLET_RETURN`, не по arrival в модуль.

Hedge, NUM, online rescheduling, SQA/QPU, ML и полноценный IDS DAG — следующий этап.
Для Hedge недостаточно выбрать эксперта: нужны корректная модель обратной связи,
учёт стоимости оценки неисполненных экспертов и различие surrogate regret и
качества независимого контрфактического расписания. Гарантия Q-GARS сюда не переносится.

## Запуск

```bash
.venv/bin/python -m fogids.cli ids-demo
.venv/bin/python -m unittest discover -s tests -v
```

Другой вход/каталог: `fogids ids-demo --config configs/ids-small.json --output artifacts/my-run`.
Повторный запуск перезаписывает одноимённые артефакты. В каталоге результатов:
копия config, QUBO с labels/offset, CSV назначений и завершений, Java logs, `summary.json`.
Выбор SA воспроизводится по seed; измеренное wall-clock время зависит от машины.
Один синтетический батч — smoke experiment, не доказательство научного превосходства.
